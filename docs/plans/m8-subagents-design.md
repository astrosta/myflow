## 1. M8 到底在解决什么

**目标一句话：lead agent 能把子任务丢给独立上下文的子代理。**

子代理的价值只有三条，**其它都是幻觉**：

| 收益 | 什么时候真的成立 |
|---|---|
| **并行延迟** | 3 个互不依赖的调研任务同时跑 |
| **专家能力** | 某个子代理有更强的模型或更专的提示词 |
| **上下文隔离** | 一个会产生几万 token 中间垃圾的任务，只把结论带回来 |

对应的成本也是实打实的：启动开销、重复发现（子代理不知道 lead 已经查过什么）、
结果综合的额外一轮、状态冲突、副作用重复。

**所以委派必须被定位成一种优化，而不是"任务复杂就委派"的默认反应。**
这一条要写进 lead 的提示词、`task` 工具的描述、以及每个内置子代理的角色描述，三处保持一致。

两个**硬否决**（不是"成本"，是"不许"）：

- **输出依赖**：B 需要 A 的结果 → 不能并行派发
- **可变状态重叠**：两个子代理会写同一个文件 → 不能并行派发

重复发现和"直接做更便宜"是成本项，要权衡，但不是否决项。
一串有边界的顺序步骤可以放进**一个**子代理里跑，如果隔离收益足够明显。

### 两周排期

| 天 | 内容 |
|---|---|
| D1–2 | 注册表 + `task` 工具骨架 + 两个 ID 的契约 |
| D3–5 | **执行器：隔离事件循环、checkpoint 血缘、上下文拷贝**（最难的部分） |
| D6–7 | 并发控制、超时、取消、沙箱共享生命周期 |
| D8 | 事件流：`task_*` 自定义事件 + namespace 保留 + 持久化 |
| D9 | 护栏上限与 `stop_reason` |
| D10 | token 归属、步骤捕获、测试收口 |

## 2. 两个 ID，绝对不能合并

这是整个 M8 最便宜也最容易被跳过的一个决定。**第一天就要定下来。**

| ID | 由谁生成 | 用途 |
|---|---|---|
| `tool_call_id` | **provider**（模型返回的） | 对外相关性键：`ToolMessage`、`task_*` SSE 事件、持久化的生命周期事件、前端卡片、扩展契约的 `scope_id` |
| `execution_id` | **服务端生成**（UUID） | 注册表主键：轮询、取消、超时、清理 |

**为什么不能合并**：provider 的 `tool_call_id` 在不同父 run 之间**不保证全局唯一**。
拿它当注册表的所有权键，两个并发的 run 撞上同一个 id 时会互相取消对方的子代理——
而且这个 bug 只在高并发下偶发，事后从日志里几乎看不出来。

推论一条：**调度闭包要持有自己的结果对象，不要再通过可变注册表反查所有权。**

```python
# ✗ 每次都回注册表查，注册表在此期间可能已被别人改写
result = registry[execution_id]

# ✓ 闭包捕获结果对象本身
def _on_done(fut, result=result):
    result.set_terminal(...)
```

## 3. 子代理不是一次新的 run

**子代理不占用 M3 定义的"每 thread 一条活跃 run"的名额。**

它是 lead 图**内部**的一次委托，不是新的 `/runs`。进度通过 root namespace 上的
`custom` SSE 事件（`task_started` / `task_running` / `task_completed` …）汇报。

把子代理做成真正的 run 会立刻撞上 M3 的单活跃操作约束——lead 自己正占着名额，
它派出去的第一个子代理就会被拒。绕过那个约束等于放弃 M3 的并发模型。

### 3.1 流式透传时必须保留 namespace

如果要把子图的帧透传给客户端，SSE 事件名必须是 `values|<ns>`（LangGraph Platform 风格），
**不能是裸 `values`**。

被委托的子代理继承了父 checkpoint namespace。把它的 `values` 快照发成裸 `values`，
SDK 客户端会用**子代理的局部状态覆盖整个会话视图**——用户会看到自己的对话历史
突然变成子代理那几条消息。

对称的要求：所有只关心根帧的消费者都要**忽略带 namespace 的帧**。至少这几个：

- 文件工具的分块合批
- 子代理事件持久化（否则子代理事件会被自己二次记录）
- LLM 错误降级检测

## 4. 执行器：三个跨边界问题（D3–5）

这是 M8 真正难的地方。子代理运行在一个**独立的持久事件循环**上，
和父 run 的循环之间有三条边界要处理。

### 4.1 为什么要独立循环

子代理是一个完整的 agent 图，会跑几十上百轮。放在父 run 的循环上意味着
它的每一次 `await` 都和父 run 的流式推送、心跳、SSE 消费抢同一个循环。
更麻烦的是父 run 结束时循环会被拆掉，而子代理的清理逻辑还需要跑。

方案：**一个进程级的持久隔离循环**，所有子代理协程提交到它上面。

### 4.2 边界一：ContextVar 要拷贝，但要摘掉绑定循环的回调

提交前把环境 ContextVar 拷贝进隔离循环，这样 checkpoint 血缘、用户身份、
追踪上下文、tags/metadata、以及 LangGraph 自己的 namespace 消息流处理器都能存活。

**但要摘掉标记为"绑定父循环"的回调处理器。** 典型的就是 run journal——
它持有父循环上的任务和一个 SQL 连接池。让它跨循环会导致：

- 重复计账（LangGraph 会把继承的回调和子 run 自己的 token 收集器合并）
- `Future attached to a different loop` 崩溃

**但也不能图省事传一个空白 `Context`**：继承的 checkpoint namespace 和框架的
流处理回调是 §3.1 那个契约的前提，丢了它们子代理的帧就发不出去了。

做法是给需要摘除的处理器打一个显式标记，拷贝时按标记过滤——
而不是维护一个类名黑名单。

### 4.3 边界二：checkpoint 血缘——**不要**在子配置里重新指定坐标

这是一个纯粹靠踩坑才知道的点：

```python
# ✗ 即使传的是同一个 parent thread_id，也会开启一条新的根血缘
child_config = {"configurable": {"thread_id": parent_thread_id, ...}}

# ✓ 完全省略 checkpoint 坐标键，让 LangGraph 从拷贝来的 ContextVar 继承
child_config = {"configurable": {...非坐标的键...}}
```

要省略的四个键：`thread_id`、`checkpoint_ns`、`checkpoint_id`、`checkpoint_map`。

显式重新提供它们（**哪怕值完全一样**）会在较新的 LangGraph 上开启一条新的根血缘，
子代理就失去了非根的子图 namespace——然后它的 AI/tool 帧会被路由进**父 run 的
`messages` 流**，回到 §3.1 那个"覆盖整个会话视图"的故障。

DeerFlow 的业务组件（沙箱、中间件、归属统计）仍然需要父 `thread_id`，
但它们应该从 `runtime.context` 拿，不是从 `RunnableConfig`。

这条要写一个回归测试钉住——它依赖上游行为，升版本时要能立刻发现。

### 4.4 边界三：子代理图用 `checkpointer=False` 编译

子代理是一次性的，永远不会 resume。继承父 run 的 checkpointer 只会把
子代理的中间状态写进父 thread 的 checkpoint 表，污染历史又浪费存储。

### 4.5 反向边界：延迟清理要钉在隔离循环上

轮询器意外退出时，注册表清理要提交到**隔离循环**执行，
因为 `asyncio.run()` 退出时会取消调用方循环上的任务——
在那里 `create_task` 的清理逻辑会在跑起来之前就被取消。

而最终的 token 用量报告要走**相反方向**：在展开时捕获父 run 的循环，
用 `call_soon_threadsafe` 交回去。原因是账本的累加器是无锁的读-改-写字段，
从隔离循环或工作线程写它会静默丢失 token 更新。

清理闭包只捕获"解析好的用量记录器 + 几个 id + 捕获的循环"，
**不要捕获整个 runtime**——清理任务可能存活到完整的轮询预算结束，
通过 runtime 它会把父 run 的账本和事件存储钉住那么久。

## 5. 并发控制：两个独立的上限（D6）

### 5.1 并发数 vs 总量

| 上限 | 约束的是 | 默认 |
|---|---|---|
| `max_running` | **同时**在跑几个（进程级） | 3 |
| `max_total_per_run` | 一次父 run **累计**派了几个 | 6 |

只有并发上限是不够的：一个长 lead run 可以在每个规划检查点都发起一批合法大小的委派，
跑一整天。总量上限堵的就是这个。

总量按**当前 run** 的委派台账计，**同 thread 里历史 run 的委派不消耗新 run 的预算**。

并发数一次解析为三者的最小值：每次请求的要求、启动时冻结的配置值、schema 安全上限。
**热重载不能让任何一层宣告比已创建的进程控制器更多的容量**——
提示词说"你可以并发 8 个"而控制器只有 3 个槽，模型会一直撞墙。

### 5.2 准入控制器

进程级的**异步 FIFO 准入控制器**，有界队列。两条要求：

- **等待者不占调度线程**（纯 async 等待，不是线程池阻塞）
- **取消和超时必须释放队列位置和槽位所有权**

### 5.3 槽位耗尽时不要报错

没有委派额度时，正确的做法不是抛异常，而是：

1. 剥掉本轮的 `task` 工具调用
2. 同步 provider 的原始 tool_call 元数据（否则会留下悬空调用，见 M6 §5.1）
3. 强制 `finish_reason="stop"`
4. 追加一条可见的"已达委派上限"说明

这样模型会拿已经收到的结果去综合，而不是看到一个错误然后重试。

## 6. 共享沙箱的生命周期（D7）

子代理和 lead **共用同一个 thread 沙箱**（它们在同一个 thread 上工作）。
这带来一个具体问题：**一个子代理跑完了，不能把沙箱关掉——兄弟还在跑。**

方案是引用持有：每个准入的子代理携带一个稳定的、从任务派生的
`sandbox_lease_owner_id`，沙箱中间件按这个 id 对 provider 客户端登记一次持有。
**最后一个持有者**执行真正的释放。

配套三条：

**命令作用域要分开。** 每个子代理有自己的 `command_scope_id`。
在支持持久 shell 会话的 provider 上，这意味着每个子代理挑一个独立的 shell 会话——
独立作用域可以并发跑，而单个子代理内部的 shell 状态仍然保序。

**`to_thread` 里的同步沙箱调用要 shield 并排空。** 否则一个被取消的 worker
可能在子代理已经终态化之后才真正执行完，去释放一个已经被释放的持有者。

**释放要幂等，且在 `finally` 里重复一次。** 中间件正常路径会释放，
但异常、协作式取消、超时展开这三条路径都可能绕过它。执行器在 `finally` 里
再释放一次（幂等），才能保证不泄漏租约。

## 7. 护栏上限与 `stop_reason`（D9）

三条独立的轴都能让子代理提前结束。

| 轴 | 机制 | 抛异常吗 |
|---|---|---|
| **轮次** | `recursion_limit = max_turns`，耗尽时 LangGraph 抛 `GraphRecursionError` | **会**，要专门 catch（在通用 `except` 之前） |
| **token** | token 预算中间件，到硬上限时剥掉工具调用、强制 `stop` | 不会 |
| **循环** | 循环检测中间件，识别重复的工具调用集合 | 不会 |

后两者**故意不抛异常**——让本轮自然产出一个最终答复，比丢一个异常给用户有用得多。

### 7.1 用附加字段，不要加状态枚举

三条轴触发时，状态仍然是正常的 `completed` / `failed`，
**另外**带一个 `stop_reason`（`turn_capped` / `token_capped` / `loop_capped`）。

理由是兼容性：新增一个状态枚举值会让所有已有的消费者（前端、台账读取器、
跨语言契约）遇到未知值；一个可选字段会被老消费者直接忽略。

- 有可用的最终答复（哪怕是从最后一个流式块里恢复的部分结果）→ `completed` + `stop_reason`
- 什么都没剩下 → `failed` + `stop_reason`

### 7.2 护栏的发现方式要解耦

每个护栏中间件暴露一个按 run_id 的 `consume_stop_reason(run_id)` 方法。
执行器用 **duck typing**（`hasattr`）收集所有有这个方法的中间件，取第一个非空的原因。

这样以后加一条新的护栏轴，执行器一行都不用改，也不需要 import 那些护栏类。

### 7.3 台账要把 `stop_reason` 渲染给模型看

lead 必须知道"这个结果是撞了上限的部分结果"，而不是当成干净的完成。
台账条目要渲染一句面向模型的指引：*"命中护栏上限并带回部分结果；
可以复用它、收窄范围重试、或调高该 agent 的预算。"*

## 8. 几个会静默出错的细节

### 8.1 图干净地结束 ≠ 子代理成功

M6 的 LLM 错误处理中间件会**故意**把 provider 异常转成一条 `AIMessage`，
让图能干净地结束。子代理执行器如果只看"图有没有抛异常"，会把这种情况判成成功。

正确做法：终态化时检查最后一条 assistant 消息上的**错误降级标记**
（`additional_kwargs` 里那个由框架打的 bool），有标记就映射为 `failed`。

**只有标记是权威的。** 看起来像错误的 assistant 散文没有标记就是正常完成——
执行器和前端都不许把展示文本当状态协议解析。

### 8.2 token 归属：走消息状态，不要用全局缓存

子代理的 token 要归到**父 run** 上，通过 `ToolMessage.additional_kwargs` 传递，
不要用进程级的全局缓存。

全局缓存在并发子代理下会串号，而且父 run 结束后缓存条目的清理时机没有正确答案。

顺带：终态 `ToolMessage` 的元数据里要留 `subagent_model_name` 和
`subagent_token_usage`，这样重新加载会话后前端卡片还能显示。
**provider 没给用量就留空，不要估算成 0**——0 和"未知"是不同的信息。

### 8.3 步骤捕获要走新增的尾部，不是 `messages[-1]`

一轮里模型可能调了 3 个工具，LangGraph 的 ToolNode 会在**一个超级步**里
追加 3 条 `ToolMessage`。只看 `messages[-1]` 会丢掉前两条。

正确做法是每个 `values` 块都走**新追加的那一段尾部**。

**还有一个收缩问题**：如果子代理也启用了摘要压缩，压缩会用
`RemoveMessage(REMOVE_ALL_MESSAGES)` 重写整个消息通道，
`len(messages)` 会突然**小于**捕获游标。

检测到收缩（`total < processed_count`）时把游标重置到新的尾部，
靠 id/内容去重防止重发压缩前的步骤。不这么做的话，
压缩之后新产生的步骤会一直被丢弃，直到 `total` 重新超过那个陈旧的游标。

### 8.4 子代理共享父 thread_id，所以记忆刷写要跳过

如果启用了长期记忆，lead 的压缩钩子会把压缩掉的消息按 `thread_id` 刷进持久记忆。
子代理共享父 `thread_id`，不跳过这个钩子的话，
**子代理的内部轮次会污染父 thread 的长期记忆**。

构建子代理中间件链时显式传 `skip_memory_flush=True`。

### 8.5 调用方策略要快照进 run 元数据

一个自定义 lead agent 可以声明 `allowed_subagents`：
`None` = 全部允许，`[]` = 硬拒绝，列表 = 白名单。

**这个策略要在 run 开始时快照进 run 元数据，`task` 工具内部绝不重新读可变的 agent 配置。**
否则运行中途有人改了配置，同一次 run 的前后两次委派会用不同的策略。

策略要同时过滤**提示词里的发现**和**`task` 的执行**——只过滤一边，
要么模型看得见却调不动（浪费轮次），要么看不见但能调（策略形同虚设）。

### 8.6 事件持久化要批量写

一个深度子代理（`max_turns=150`）会在热流循环上产生几百个步骤事件。
逐条 `put()` 意味着几百次 per-thread 的咨询锁获取。

用 `put_batch`，在三个时机 flush：终态事件、达到阈值条数、worker 的 `finally`。

这些事件用独立的 `category`，这样它们不会出现在 thread 的消息流里，
但前端展开卡片时能按 `task_id` + `after_seq` 游标分页拉回来。

## 9. 测试清单

| 文件 | 覆盖 |
|---|---|
| `test_subagent_ids.py` | 两个 run 用相同的 `tool_call_id` 并发委派，互不干扰 |
| `test_subagent_lineage.py` | **子配置不含四个坐标键**；子代理帧不进父 `messages` 流；`checkpointer=False` |
| `test_subagent_loop_boundary.py` | ContextVar 拷贝保留流回调；绑定循环的处理器被摘除；无重复计账 |
| `test_subagent_concurrency.py` | 并发上限；总量上限；历史 run 不消耗新预算；槽位耗尽时剥调用而非报错 |
| `test_subagent_sandbox.py` | 一个子代理结束不关闭沙箱；最后一个持有者释放；取消/超时不泄漏租约 |
| `test_subagent_cancel.py` | **取消父 run，所有子代理被清理**；取消释放队列位置 |
| `test_subagent_stop_reason.py` | 三条轴各自的 `stop_reason`；有部分结果 → completed，无 → failed |
| `test_subagent_error_marker.py` | 带降级标记 → failed；看起来像错误的散文 → completed |
| `test_subagent_step_capture.py` | 一轮多工具全部捕获；压缩收缩后游标重置且不重发 |

`test_subagent_lineage.py` 和 `test_subagent_cancel.py` 是这一阶段最值得写的两个。
血缘那个要驱动一个真实的父图，断言子帧**没有**出现在父 `messages` 流里——
只断言配置字典里没有那四个键是不够的，那只能防住改代码，防不住升级 LangGraph。

- [ ] 中途取消父 run，**所有子代理被清理**，没有残留的沙箱租约或注册表条目
- [ ] 前端会话视图在子代理运行期间不被子代理的局部状态覆盖
- [ ] 父 run 的 token 统计包含子代理的消耗，且刷新页面后卡片仍显示用量
- [ ] 一个必定超轮次的子代理，返回 `completed` + `turn_capped` 和部分结果
- [ ] 一个 provider 报错的子代理，返回 `failed`，而不是一条看起来正常的完成
- [ ] 两个子代理并发写沙箱，先结束的那个不影响后一个

第二条建议专门做一次压力验证：起 3 个长任务，在第 2 秒取消，
然后检查沙箱 provider 侧的会话数和注册表条目数都归零。

---

## 11. 刻意不做的事

| 不做 | 理由 |
|---|---|
| **持久化批量委派**（`batch_task` + 租约服务 + 重试预算） | 那是一整套独立的租约状态机 + 数据表 + 恢复语义，够单独一个里程碑 |
| **验收标准的确定性校验** | 真要把"文件存在"" 测试通过"做到不可伪造，需要 shell 结构解析、执行证据溯源、符号链接规范化——这是一个研究级的工作量 |
| **工具回执与引用校验** | 同上，属于"可验证性"这条独立的产品线 |
| 子代理嵌套委派 | 内置的 `general-purpose` 显式**不**带 `task` 工具。递归委派的成本模型和取消语义都要重做 |
| 子代理 resume | 一次性语义是 `checkpointer=False` 的前提，要 resume 就得整套重来 |
| 子代理继承请求级密钥 | M7 §6 明确了不继承。子代理的密钥边界需要单独设计 |

前两条要在代码里留出接口位置（`stop_reason` 的附加字段模式、
终态 `ToolMessage` 的元数据槽），但不要为它们提前建表。

---

## 12. 一句话总结

M8 的实现难度集中在**一条边界**上：子代理跑在独立的事件循环里，
而它需要继承父 run 的 checkpoint 血缘、流回调和身份，
同时又不能继承父 run 的账本、checkpointer 和消息通道。

检验标准只有一个：**在子代理运行期间，用户的会话视图不能被它的局部状态覆盖；
取消父 run 之后，沙箱会话数和注册表条目数都归零。**
这两条过了，剩下的都是可以增量补的。
