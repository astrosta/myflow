## 1. M7 的范围

**目标一句话：不改代码就能给 agent 加能力。**

两条互补的路径，解决的是不同的问题：

| | MCP | 技能 |
|---|---|---|
| 加的是什么 | **新工具**（外部进程/服务提供） | **新知识**（prompt 片段 + 附带资源） |
| 谁来写 | 第三方服务端 | 你自己，或社区 |
| 载体 | 一个进程或 HTTP 端点 | 一个目录 + `SKILL.md` |
| 成本 | 要装、要配凭据、要管连接 | 写个 markdown 就行 |

**技能是这两者里投入产出比最高的。** 一个目录加一个 markdown 文件，
就能让 agent 掌握一套领域流程（怎么处理 PDF、怎么写周报、怎么调某个内部系统）。
MCP 更强但更重——它带来的是连接管理、凭据注入、进程生命周期这一整套问题。

### 两周排期

| 天 | 内容 |
|---|---|
| D1–2 | **运行时可写配置的并发写**（两者共同的地基） |
| D3–5 | 技能：加载、解析、注入、slash 激活、`allowed-tools` 策略 |
| D6–8 | MCP：客户端、三种 transport、缓存失效、工具名前缀 |
| D9 | MCP 凭据层次 + fail-closed |
| D10 | 工具检索（`tool_search` + 延迟提升），如果工具数量已经上百 |

## 2. 共同地基：运行时可写配置（D1–2）

**这一节看起来最无聊，但它是 M7 唯一真正会导致数据丢失的部分。**

MCP 服务器列表和技能的启用状态都存在 `extensions_config.json` 里，
这个文件**同时被 Gateway API 和运行时读写**。用户在网页上点一下"启用某技能"，
就是一次读-改-写。

### 2.1 三个必须同时满足的条件

**① 每次读-改-写必须同时持有进程内锁和跨进程文件咨询锁。**

只有进程内锁的话，多 worker 部署下两个进程各自读到旧版本、各自改一个字段、
各自写回——后写的把先写的改动覆盖掉。用户会看到"我明明启用了，刷新一下又关了"。

锁的范围必须覆盖**完整的读-改-写-重载循环**，不是只覆盖写的那一下。

**② 原子写：同目录临时文件 + fsync + `os.replace()`。**

直接覆写原文件意味着写到一半崩溃会留下一个截断的 JSON——
下次启动时整个配置解析失败，所有 MCP 服务器和技能状态全丢。

`os.replace()` 还要保留原文件的权限位和符号链接目标。

**③ Docker 挂载单文件时，`rename()` 会返回 `EBUSY`。**

这是个很具体的坑：Docker 把单个文件（不是目录）挂载进容器时，
那个文件是一个独立的 mount point，Linux 的 `rename()` 对它返回 `EBUSY`。

所以要保留"临时文件 + rename"作为主路径，**只在收到 `EBUSY` 时**退化为就地覆写。
那条退化路径**不是原子的**，只在别无选择时用；**其它 errno 必须抛出**，
不能笼统 catch 一个 `OSError` 就退化——那等于永远走非原子路径。

### 2.2 缓存失效用内容签名，不用 mtime 比较

```python
ConfigSignature = tuple[float | None, int | None, str | None]   # (mtime, size, sha256)
```

这是 M0 已经建立的机制，M7 复用同一个 helper。

**严格的 `mtime >` 比较会漏掉一大批真实场景**：同一秒内的两次编辑、
`git checkout` 让 mtime 倒退、`cp -p` / 备份恢复、`tar` / `rsync`、
网络挂载和对象存储的 mtime 不可靠、以及切换到另一个 mtime 更老的配置文件。

比较"解析后的路径 + 内容签名"两者是否和初始化时记录的一致。

还有一个边界：如果加载过程中发现签名变了（前后两次快照不一致），
**丢弃这次加载的结果时必须走和正常失效一样的会话退役路径**。
否则一次被放弃的加载会把它创建的连接留在池子里，下一次构建工具时会用到。

## 3. 技能系统（D3–5）

### 3.1 形状

```
skills/
├── public/                    # 提交进仓库
│   └── pdf-processing/
│       ├── SKILL.md
│       └── scripts/extract.py
└── custom/                    # gitignored，per-user
```

```markdown
---
name: PDF Processing
description: Handle PDF documents efficiently
license: MIT
allowed-tools: [read_file, write_file, bash]
argument-hint: "<file path>"
---

# Skill Instructions
...
```

**技能文本一律按 UTF-8 处理。** 读写都显式传 `encoding="utf-8"`，
不要依赖平台 locale——Windows 上默认是 GBK，中文技能会直接乱码或抛异常。
这条要写进项目规范，因为它会在每个新加的读写点上重犯。

### 3.2 加载：两个容易忽略的规则

**技能目录是一个包边界：嵌套的 `SKILL.md` 不注册为运行时技能。**
一个技能包里可能带着示例、测试 fixture、子模板，它们里面的 `SKILL.md`
不应该变成用户能启用的独立技能。扫描时遇到一个 `SKILL.md` 就停止向下递归。

**符号链接要区分对待。** 允许技能目录本身是一级符号链接
（运维管理的技能树经常这么组织），但激活时要拒绝符号链接的 `SKILL.md`
和任何更深层的路径逃逸。

### 3.3 两种发现模式

| 模式 | 系统提示词里放什么 | 模型怎么拿到全文 |
|---|---|---|
| **全量注入**（默认，简单） | 每个技能的完整元数据 + 路径 | 直接就有 |
| **延迟发现**（技能多了以后） | 只有名字列表 | 调 `describe_skill` 拿元数据，再 `read_file` 读全文 |

**M7 先做全量注入，把延迟发现的开关和 `describe_skill` 工具留出来。**

延迟发现的价值在技能超过二三十个时才体现：全量元数据会占掉几千 token，
而且**每加一个技能整个系统提示词的前缀缓存就失效一次**。
延迟发现只放一个紧凑的名字索引，保持前缀稳定。

这和 M6 §4.3 的"基础系统提示词必须完全静态"是同一个考量。

### 3.4 激活：两条路径，权威性不同

**Slash 激活**：用户输入 `/pdf-processing 把这个文件转成文本`。
严格语法解析，只对本次模型调用加载那个技能的 `SKILL.md`。

解析器要拒绝：前导空白、缺少分隔符、保留的频道命令（`/new`、`/help` 等）、
未启用的技能、不在当前 agent 白名单里的技能。

**自主读取**：模型自己判断需要，用 `read_file` 读了某个 `SKILL.md`。

两者的区别在下一节。

### 3.5 `allowed-tools` 是行为约束，不是安全边界

这是技能系统最需要想清楚的一点。

**规则一：`allowed-tools` 只对"真正激活"的技能生效。**
被动启用的技能、以及 agent 配置里列出的技能白名单，**不收紧基线工具集**。
否则用户启用了一个只声明了 `read_file` 的技能，整个 agent 就失去了写文件的能力——
这显然不是"启用一个技能"该有的语义。

**规则二：slash 激活的策略是支配性的。**
用户显式 `/some-skill` 之后，模型再去读别的 `SKILL.md`
**不能扩大**当前的工具权限。否则一个受限技能可以通过"读另一个技能"来越权。

没有 slash 激活时，自主捕获的技能之间用并集语义。

**规则三（最重要）：这是 best-effort 的行为约束，不是安全边界。**

理由很直接：模型可以用 `bash cat /mnt/skills/xxx/SKILL.md` 读取技能全文，
这条路径不会被捕获。而且自主捕获的技能上下文是有容量上限的，老条目会被驱逐。

**必须在文档和代码注释里明确写出这一点。** 把它当安全边界用——
比如"用受限技能来隔离不可信用户"——是错误的，真正的边界是沙箱和鉴权。

### 3.6 框架工具 vs 业务工具

即使在最严格的技能策略下，`tool_search` 和 `describe_skill` 也要保持可用——
它们是发现基础设施，没有它们模型就瞎了。

但**发现不等于可用**：一个通过 `tool_search` 发现的业务工具，
仍然需要当前激活策略的显式声明才能出现在 schema 里或被执行。

`task`（委派给子代理）**不是框架豁免的**。否则一个受限技能可以通过委派绕过自己的策略。

## 4. MCP（D6–9）

### 4.1 基础

用 `langchain-mcp-adapters` 的 `MultiServerMCPClient`，支持 stdio / SSE / HTTP 三种 transport。
工具**懒加载**（首次使用时），按 §2.2 的内容签名失效。

**工具名默认加 `<server_name>_` 前缀。** 两个 MCP 服务器都提供一个叫 `search` 的工具
是很常见的，不加前缀会在 M2 §8.1 的去重逻辑里被静默丢掉一个。

给一个 per-server 的开关允许关掉（有些服务器的工具名本身就带稳定命名空间），
但**源路由和会话包装必须按"哪个服务器产生的"来判断，绝不能靠"工具名是否以前缀开头"**——
关掉前缀的服务器会让后者全盘失效。

### 4.2 stdio 的三件事

**会话按 `(server_name, user_id:thread_id)` 作用域。**
stdio 服务器是有状态的子进程，不同会话共用一个进程会串数据。

**固定 `cwd` 和临时目录。** stdio 子进程的默认 `cwd` 指到 thread 的 workspace，
`TMPDIR`/`TMP`/`TEMP` 指到 workspace 下的一个内部目录
（除非运维显式配了）。不这么做的话，MCP 服务器写的文件会散落在 Gateway 进程的
工作目录里，用户在自己的 workspace 里看不到。

那个内部目录要从"工作区变更摘要"里排除——它是过程产物，不是用户的成果。

**断连恢复要精确。** 收到明确的 `Connection closed` 错误时，
只驱逐**那一个** `(server, user:thread)` 会话，而且**只在注册表里的条目
仍然是失败的那个 session 对象时**才驱逐。

否则一个并发的老调用晚到的错误会把刚建立的替代会话干掉。失败的那次调用
照常向上报错，**绝不自动重放**——重放一个有副作用的工具调用比报错糟糕得多。

普通的 `isError=true` 工具结果和协议超时**不驱逐**健康会话。

### 4.3 凭据：四层优先级，全部 fail-closed

```
静态 headers  <  oauth  <  per-user  <  per-request
```

| 层 | 用途 |
|---|---|
| 静态 `headers` | 启动时的工具发现 |
| `oauth` | token 端点流程，自动刷新 |
| `user_auth` | 按 DeerFlow 用户映射凭据 |
| `headers_from_context` | 按请求传（多租户网关、每次运行不同的 key） |

三条纪律：

**Fail-closed 是默认。** 映射里找不到当前用户、或解析出空值，
要抛 `ToolException`，而不是静默回落到发现用的那个凭据——
后者意味着一个租户的调用用了另一个凭据的权限在跑。

需要放行的场景给一个显式的 `on_missing: "passthrough"` 开关。

**Header 名大小写不敏感，这个坑很隐蔽。** 静态配置写了 `authorization`、
注入的写 `Authorization`，两个都会到达 httpx——适配器是用
`{**static, **override}` 简单合并的。服务端用单值访问器读这个字段时拿到的是**静态那个**，
优先级被静默反转了。

解法是所有凭据注入都走一个统一的 `apply_header_overrides`，
它会丢掉只有大小写不同的键，并沿用连接已经在用的那个拼写。

**凭据值非法时绝不能回显。** 这是我认为整个 M7 里最值得注意的一个安全细节：

> 传输层（h11）在 header 值含换行或首尾空白时抛的异常，**消息里带着完整的值**。
> 而 M6 的 `ToolErrorHandlingMiddleware` 会把工具错误抄进模型可见的消息。
> 两者一叠加，一个格式错误的凭据就会进入提示词、checkpoint 和 trace。

所以要在渲染出最终 header 值之后、送进传输层之前做一次合法性检查
（换行、首尾空白、非 ASCII），不合法就**只报原因不报值**。
检查的对象是**渲染后的完整值**（`<token_type> <access_token>`），
不是分开检查两个字段——因为传输层看到的是前者。

这个检查点要唯一：OAuth 管理器、工具拦截器、初始发现、后台任务路径,
全都从同一个函数拿值。

### 4.4 拦截器里怎么读运行时上下文

一个具体的 API 陷阱，会浪费半天时间：

```python
# ✗ 错的：工具调用内部这个键是 None
context = get_config()["context"]

# ✓ 对的：运行上下文挂在 runtime 上
runtime = request.runtime      # LangGraph 会注入到名为 runtime 的参数
```

运行上下文挂在 LangGraph runtime 上，**不在**传播给子 runnable 的 `RunnableConfig` 里。
这一条建议写一个测试钉住（驱动一个真实的适配器工具走一遍真实的图），
因为它依赖上游的参数注入约定，改名了要能立刻发现。

### 4.5 API 注册 stdio 服务器的启动校验

配置文件可以写任何东西（那是运维的文件），但 **HTTP API 是不可信输入**。
通过 API 注册一个 stdio 服务器时要校验三样：

1. `command` 必须是允许列表里的裸可执行文件名（默认 `{npx, uvx}`），
   拒绝路径分隔符、空白、shell 元字符
2. `args` 里不能有任意执行类的 flag
3. `env` 里不能有代码注入类的变量名（`PYTHONPATH`、`PYTHONHOME` 这类
   在解释器启动时**无条件**执行调用方代码的）

后两条存在是因为**第一条只约束了二进制的名字，没约束那个二进制去跑什么**。

> **这是纵深防御，不是信任边界。** `npx`/`uvx` 存在的意义就是拉取并执行远程包，
> 管理员完全可以指向一个自己发布的包。真正的边界是**管理员认证 + 网络可达性**。
> 不要以为加了这个检查就可以把 MCP 注册开放给不可信的管理员——不能，
> 而且那个问题的解法也不是更长的黑名单。

**M7 的建议：先只做第 1 条（命令允许列表）。** 后两条的正确实现相当微妙
（`npx` 在包名处停止解析自己的 flag，所以只能筛选它自己的选项区，
而确定选项区边界又需要知道每个 flag 的元数），
在你真的要把 MCP 注册开放给非运维角色之前不值得投入。

## 5. 工具检索（D10，按需）

**触发条件：MCP 工具数量上百。** 全量塞进 tool schema 会占掉几万 token，
而且模型在一百个工具里选对的准确率会显著下降。

方案是**延迟工具提升**：

1. MCP 工具的 schema 默认对模型隐藏
2. 提供一个 `tool_search` 工具，模型描述需求，返回匹配的工具
3. 被检索到的工具"提升"进当前 thread 的可见集合（记在 state 里）
4. 后续轮次这些工具直接可见

配一个可选的路由中间件：根据用户最新消息**自动提升**明显匹配的工具，
省掉一次 `tool_search` 往返。它只做提升，不执行任何工具。

提升记录要按工具目录的哈希做作用域——配置变了之后，
上一次提升的工具名可能已经不存在了。

## 6. 请求级密钥（接口预留）

技能脚本有时需要终端用户的短期凭据（比如一个内部系统的 token）。
把它写进提示词是不可接受的——它会进 checkpoint、进 trace、进日志。

完整实现不在 M7 的必做范围，但**契约现在就要定**：

- **声明**：`SKILL.md` frontmatter 里 `required-secrets: [...]`
- **携带**：运行请求的 `context.secrets`，**绝不放进消息**
- **绑定**：三重门——技能被运维**启用** × 调用方**按请求提供**了值 ×
  名字在 frontmatter 里**声明过**，取交集
- **注入**：通过 M2 的 `execute_command(env=...)`，不拼进命令字符串

两个配套要求现在就该有（M2 已经做了一半）：

**继承环境要擦除。** M2 §5.3 的 `build_sandbox_env` 已经在做，
M7 只需确认技能脚本走的是同一条路径。

**绑定要每次模型调用重算。** 不能算一次然后一直用——
技能被逐出上下文、或调用方停止提供某个值，下一次调用就应该失去注入。

还有一条关键的安全推论：**绑定时要用规范化路径去实时注册表里查那个技能，
而不是信任上下文里存的数据。** `runtime.context` 是调用方可合并的，
一个伪造的"已激活技能"记录如果被直接采信，就等于任意密钥注入。
按注册表解析让伪造变得无害。

## 7. 测试清单

| 文件 | 覆盖 |
|---|---|
| `test_config_concurrent_write.py` | **并发读-改-写不丢更新**；崩溃中断不留半截文件；`EBUSY` 退化路径；其它 errno 抛出 |
| `test_config_signature.py` | 同秒编辑、mtime 倒退、切换到更老的文件——全都判定为已变更 |
| `test_skill_loading.py` | 嵌套 `SKILL.md` 不注册；一级符号链接目录可用；深层路径逃逸被拒；**UTF-8 中文技能** |
| `test_skill_policy.py` | 被动启用不收紧工具集；slash 策略支配；`task` 不豁免；框架工具始终可用 |
| `test_mcp_tool_prefix.py` | 同名工具不冲突；关掉前缀后源路由仍然正确 |
| `test_mcp_stdio_session.py` | 会话按 `(server, user:thread)` 隔离；断连只驱逐自己；晚到的旧错误不误伤替代会话；失败不自动重放 |
| `test_mcp_credentials.py` | 四层优先级；缺失时 fail-closed；**非法凭据值不出现在任何错误消息里** |
| `test_mcp_runtime_context.py` | 驱动真实适配器工具走真实的图，断言 `request.runtime` 拿得到上下文 |

第一个和倒数第二个是这一阶段最有价值的两个。

`test_mcp_credentials.py` 里"非法值不回显"那一条要断言得狠一点：
构造一个带换行的凭据，然后断言完整的凭据字符串**不出现在**异常消息、
工具结果、日志输出的任何一个里。

## 8. 验收清单

- [ ] 配一个 MCP server（三种 transport 各一次），重启后工具可用
- [ ] 通过 API 启用/禁用一个 MCP server，**不重启**就生效
- [ ] 两个浏览器标签页同时切换不同技能的开关，两个改动都保住（不丢更新）
- [ ] 新建一个技能目录，模型能自动发现并使用
- [ ] 中文的 `SKILL.md` 在 Windows 上正常加载
- [ ] `/skill-name task` 激活后，该技能的 `allowed-tools` 生效；未激活的技能不影响工具集
- [ ] 故意配一个带换行的 MCP 凭据，错误信息里没有凭据内容
- [ ] stdio 服务器被 kill 掉，下一次调用报错但不影响其它会话，再下一次调用自动重建

第三条建议用脚本跑（两个并发的 PATCH 请求），手工点很难撞上竞争窗口。

## 9. 刻意不做的事

| 不做 | 理由 |
|---|---|
| MCP 长时任务（durable task） | 那是一整套租约 + 轮询 + 通知投递的状态机，本身够一个里程碑 |
| 技能静态扫描 / 安全审查 | 有社区技能分发需求时才做 |
| 技能的沙箱投影（物理隔离视图） | 需要按 agent 策略做文件级隔离，等真的有多租户需求 |
| 托管集成（预装的第三方 CLI 技能包） | 产品化功能，不是框架能力 |
| MCP stdio 的 args/env 深度校验 | 见 §4.5。在开放给非运维角色之前不值得投入 |
| 工具检索 | 见 §5。工具数量没上百就不需要 |
| 请求级密钥的完整实现 | 见 §6。但契约和三重门语义现在就定 |

## 10. 一句话总结

M7 交付两条"加能力"的路径，但它真正的风险集中在一个不起眼的地方：
**那个既被 API 写、又被运行时读的 JSON 文件。**

检验标准：两个用户同时在网页上改配置，两个改动都保住；
进程在写配置的瞬间被 kill，重启后配置完好。
这两条过不了，MCP 和技能做得再全也会在用户第一次多点几下之后丢状态。
