## 1. M5 的难点不在 UI

路线图里写的是"因为 M3 已经对齐了 Platform 协议，这里工作量主要在 UI 而不是状态管理"。
**这句话只对了一半。**

对的那一半：不用自己解析 SSE、不用自己管理重连、不用自己设计线程/运行的 API 形状。
官方 SDK 已经把这些做完了。

错的那一半：**有一件事 SDK 帮不了你，而它恰好是前端最容易出 bug 的地方——
把"持久化的历史"和"实时的流"合并成一条正确排序的对话。**

这两个来源的形状完全不同：

| | 持久化历史 | 实时流 |
|---|---|---|
| 来源 | 分页拉取的消息 feed | SSE 帧 |
| 顺序 | 服务端的全局 `seq` | 到达顺序 |
| 完整性 | 只加载了最近几页 | 只有当前这次 run |
| 身份 | 规范化的消息 id | 可能和历史里是同一条的不同副本 |

**M6 的摘要压缩会把这件事推向极端**：压缩之后的 checkpoint 可能和你已经加载的那页
历史**一条 id 都对不上**——它只保留了当前 run 的尾巴，而屏幕上那页是几轮之前拉的。

这一节（§4）占了整个 M5 一半的难度。剩下的确实主要是 UI。

### 两周排期

| 天 | 内容 |
|---|---|
| D1–2 | 项目骨架、路由、SDK 接入、单条消息能流出来 |
| D3–4 | **流模式选择 + 状态归属划分** |
| D5–7 | **消息顺序与历史合并**（最难） |
| D8 | 刷新重连、SSE gap 恢复 |
| D9 | 工具调用卡片、思考折叠、artifact 预览、文件上传 |
| D10 | nginx + 端到端验收 |

## 2. 骨架与选型

| 选择 | 理由 |
|---|---|
| **Next.js App Router** | 默认服务端组件，只有交互部分标 `"use client"` |
| **官方 LangGraph SDK** | 别手写 SSE 解析。M3 对齐 Platform 协议就是为了能用它 |
| **TanStack Query** 管服务端状态 | 缓存失效、乐观更新、分页这些不要自己写 |
| **localStorage** 管用户设置 | 设置不需要跟服务端同步 |

目录形状建议：

```
src/
├── app/          # 路由。/、/workspace/chats/[thread_id]、(auth)/login
                  # M9 加 /workspace/scheduled-tasks
├── components/
│   ├── ui/       # 从 shadcn 之类的 registry 生成，不手改，lint 忽略
│   └── workspace/# 聊天页的组件
├── core/         # 业务逻辑，这里是重心
│   ├── api/      # SDK 客户端单例 + 流模式净化 + gap 处理
│   ├── threads/  # 创建、流式、状态、历史合并
│   └── messages/ # 消息分组、顺序、工具结果查找
└── lib/
```

**`core/` 是重心，不是 `components/`。** 顺序合并、状态折叠、消息分组这些都是
**纯函数**，放在 `core/` 里可以用 node 环境的单测覆盖，跑得飞快。
混进组件里就只能靠渲染测试，慢 3 倍而且难断言。

### 一条静态根边界

根布局（`app/layout.tsx`）**不许读 cookie，也不许引入只有聊天页用的重样式**
（数学公式、代码高亮、Markdown 渲染那些 CSS）。

聊天页的样式挂在聊天路由上，落地页保持静态。否则首页会为了一个它根本不渲染的
功能加载几百 KB 的 CSS。

## 3. 流式接入：谁拥有什么

### 3.1 流模式要显式收窄

SDK 支持多种 `stream_mode`。**主聊天流要强制用增量模式**：

```
messages-tuple + updates + custom
```

**不要带 `values`。** `values` 是全量状态快照——每一帧都把整个 `ThreadState`
重发一遍。在一次几十轮的 run 里，这是几十次重复传输整个对话历史。

要注意 SDK 可能会因为"惰性追踪"自己加上 `values`，所以要在客户端包装层
**强制覆盖**成增量模式，而不是仅仅"不请求它"。

两个例外：

- 显式的状态检查（比如 §5.2 的 gap 恢复后重载）仍然用 `values`
- 用户显式请求的非快照模式（调试、任务、检查点）保留

**还有一个反直觉的约束**：后端的文件工具分块合批（M3 里那个把 `write_file`
的逐 token 输出攒成大块的优化）**是按 `messages-tuple` 触发的，不是 `values`**。
去掉快照模式不能顺手把这个也去掉，否则写一个大文件会退化成每个 token 一帧 SSE。

最后，请求前要**净化**：遇到 Gateway 不支持的模式**直接抛错**，
不要"部分转发"或者"静默退回 `values`"。后者会让一个拼错的模式名
表现为"莫名其妙变慢了"。

### 3.2 状态归属：SDK 管消息，你管其它

| 谁 | 管什么 |
|---|---|
| **SDK 的 `messages-tuple` 管理器** | 实时消息块的组装和去重。**唯一所有者** |
| **你自己的折叠代码** | 从 `updates` 帧里折叠非消息字段（artifacts、todos、目标状态…） |

第二条有个要求：**折叠时要用和后端 reducer 一致的语义**。
M1 §2 给 `ThreadState` 的每个字段定义了 reducer（去重合并、fail-closed 冲突检测、
`None` vs 空列表的区别），前端折叠 `updates` 时必须匹配那套语义，
否则前后端会显示出不同的状态。

无关的帧要在调用 SDK 的状态改写器**之前**就拒掉。

### 3.3 节流用 SDK 自带的

SDK 有一个"同一个宏任务内到达的更新先合并再通知 React"的节流模式。**用它。**

不要换成一个固定毫秒数的延迟——在连续流上那会变成尾部防抖，
表现为"模型说完了但界面还在挤牙膏"。要换的话先验证 SDK 在连续流下的行为。

## 4. 消息顺序与历史合并（D5–7）

**这是 M5 唯一一个值得画流程图的地方。**

### 4.1 问题长什么样

用户打开一个有 300 条消息的会话。你加载了最近 50 条（第一页）。
然后用户发了一条新消息，run 开始流。

现在屏幕上有三类消息：

1. **历史页**里的（带服务端的全局 `seq`）
2. **实时流**里的（还没进 feed，没有 `seq`）
3. **checkpoint 快照**里的（run 开始时的状态，可能和 1 有重叠的 id）

M6 的压缩一旦触发，第 3 类会变成"只有当前 run 的尾巴"，
**和第 1 类可能一条 id 都对不上**。

### 4.2 核心规则：位置权威是 seq 优先

```
服务端 seq  >  身份锚点编织  >  到达顺序
```

**`seq` 是服务端拥有的展示元数据。** 后端在消息进入 feed 时盖一个线程全局的
递增 `seq`，并且在它已经持久化过的 `values` 帧消息上也盖同一个值。

三条细则：

- 同一个身份出现多次时，**最早的那个 `seq` 获胜**
- 隐藏的控制副本只在没有可见副本携带位置时才贡献位置
- **`seq` 绝不写回 checkpoint**——它是展示用的，不是状态的一部分

没有 `seq` 的片段（还在流、没进 feed）回退到身份锚点编织，片段内部顺序保留。

### 4.3 两个互相打架的修复，和它们的和解

这是我认为整个 M5 最值得讲的一段，因为它是一个**先后两次修复互相推翻**的真实过程。

**第一次修复**：发现一条带 `seq` 的消息被追加到了列表尾部。
尾部**可证明是错的**——它有 `seq`，说明它在 feed 里有确定位置。于是禁止追加到尾部。

**第二次问题**：一个长会话里，用户自己的提问**凭空消失了**。
原因是第一页 50 条历史已经够不到那条消息了，而"禁止追加"的规则把它整个丢弃了。

**和解的原则**：

> **被折叠的未加载间隙可以靠翻页恢复；被丢弃的消息不能。**

所以既不能追加到尾部，也不能丢弃。正确做法是：

**一条 `seq` 低于当前加载窗口下界的实时消息，放到屏幕上所有内容的最前面**，
而不是放在"最近的锚点之前"。

而且**这个判断必须发生在锚点遍历之前，不能放在遍历内部**。
理由正是 §4.1 那个极端情况：压缩后的 checkpoint 可能和加载页一条身份都不共享，
锚点遍历**根本不会执行**——而这恰恰是一条被压缩救回的消息最需要它的 `seq` 的时候。
把判断放进遍历里，这种情况就会走到"追加到整个窗口之后"，也就是第一次修复证明错误的那个位置。

### 4.4 其它几条

**乐观消息永远在最后。** 用户刚发出、服务端还没确认的那条。

**内容替换不能丢掉已知的 `seq`、`run_id` 和运行时长。**
一条消息的内容被更新时（流式追加、压缩后重建），元数据要保留。

**历史缓存失效时保留已加载的页。** 否则已经建立的排序位置会被丢掉，
用户会看到列表重新洗牌一次。

**本地提交的那一轮要记一个身份基线。** 如果流在规范历史发布用户消息之前
就发布了新的 AI/工具步骤，只把**非基线**的可见步骤移到新的人类消息之后，
不要动历史、隐藏控制消息和重连的 run。

**动态上下文会给用户消息改 key。** M6 的动态上下文中间件把提交的用户消息
从 `X` 重命名为 `X__user`。UI 的身份匹配**只对人类消息**归一化这个保留后缀，
这样提交帧和 checkpoint 替换才是同一个可见轮次。

## 5. 刷新与重连

### 5.1 刷新不开新 run

刷新页面时，如果这个 thread 有正在跑的 run，**要 join 它、订阅当前的流**，
而不是重新发一次消息。

SDK 一般有一个挂载时重连的选项。要验证的是：join 之后 SSE 是从
`Last-Event-ID` 的断点续上，而不是从头重放整个 run
（M3 §6 定的那个缓冲区语义）。

**停止操作要立刻失效相关缓存并安排一次跟进刷新。** SDK 的停止可能通过
"abort + 发射后不管的 cancel"完成，在后端的标题生成落库之前就返回了——
只失效一次的话，侧栏里会留着"新对话"这个占位标题。

### 5.2 SSE 的 gap 帧要自己包一层

M3 §6 定义了一个 `gap` 控制帧：缓冲区已经滚过去了，客户端要的那段没了。

**上游 SDK 会忽略它不认识的事件名。** 所以要在 SDK 客户端外面包一层，
同时包住初始流和 join 的流。

收到 gap 之后：

1. 清掉过期的重连元数据
2. 发一个内部事件通知上层
3. **用 `values` 重载持久化的线程状态**（这是 §3.1 那个例外）
4. 从服务端给的保留尾部之后续；缓冲区空了就不带游标重新 join
5. 限制恢复次数（比如 5 次），避免无限循环

包装层要保持**惰性异步可迭代**，因为 SDK 是用 `for await` 消费它的。

上层要清掉乐观状态、失效历史缓存、给用户看一个恢复提示。
**绝不能让 gap 表现为一次正常的流结束**——后端的 run 还在跑，
界面显示"完成了"会让用户以为回答就这么短。

## 6. 渲染层的几个具体约定

### 6.1 消息分组：带工具调用的 AI 消息也可能有正文

一条 AI 消息可以**同时**有用户可见的文本和 `tool_calls`
（"这个方法失败了，我换一种"）。把它当成纯工具元数据处理会丢掉这些文本。

两条更细的：

**流式期间，最新人类输入之后的纯内容 AI 消息要留在"处理中"分组里**，
直到这一轮结束。provider 可能稍后往同一条消息上追加工具调用块——
过早把它归类成最终回复，会让那段文字在结束的瞬间**跳进步骤面板**。

**同样的规则适用于一次工具调用之后**：后面的纯内容 AI 消息在流式期间
保持可见，因为它自己也可能再长出一个工具调用。

### 6.2 思考过程要在答案上面，两个渲染器都是

同一条消息在生命周期里会被**两个不同的组件**渲染（流式期间是"处理中"的分组，
结束后是"已完成"的气泡）。

如果两边对"思考折叠放在文本上面还是下面"的处理不一致，
**用户会看到它们在这一轮结束的瞬间交换位置**。

规则：思考在上，它产出的答案在下。在这段思考**之前**发出的文本保持原位。

### 6.3 run 级别的展示只挂在一个锚点上

运行时长、工作区变更卡片这类东西是**按 run 解析**的。
如果按消息渲染，一次 run 里的每条 AI 消息都会渲染一份一模一样的。

要选一个锚点。注意：**一次 run 可能以多个终态 assistant 气泡结束**——
只要模型发出了一段始终没有获得工具调用的答案文本就会这样。

还有一条不显然的：**不同的展示，锚点的候选集合可以不一样**，
因为锚点只在它实际渲染的地方有用。运行时长由列表组件在每个分组周围发出，
所以它接受任何分组类型；变更卡片由单条消息组件渲染，所以它只接受 assistant。
不要为了"统一"把两者合并。

### 6.4 流式 Markdown 别用逐词包装的方案

一个很自然的实现是写个 rehype 插件把每个词包成一个 span 来做逐词动画。

**不要这么做。** 流式追加会让整个块被重新解析，旧的词会重新挂载，
动画整体重放一遍——表现为文字不停闪烁。

用渲染库自带的增量动画 API。

### 6.5 模型 / 推理等级是输入框的一部分

输入框右下角、**发送按钮左侧**放模型与推理等级选择（`model-picker.tsx`）。
取舍照 DeepSeek Harness 的 composer：一个紧凑触发器 + 两级菜单，而不是两个大下拉——
工具行高度固定，两个 select 会把输入框撑高、把附件和发送按钮挤小；触发器一行就能读完
当前选择（`模型 · 等级`）。

- **候选全部来自 config.yaml**：`/api/models` 返回 `models[].name` 与每个模型自己公布的
  `reasoning_efforts`（`{id,label,description,default}`）。前端不维护模型清单，
  也不知道哪个模型有什么等级；模型没公布候选时"推理等级"整段不出现。
- **选择只落在目录的行上**（`core/models/selection.ts`）：本地存过但已下线的模型名、
  换了模型后失效的等级，都会回退到服务端默认／`默认（不指定）`，不会把过期的值发出去。
- **"默认"= 不下发**：`context` 里只放非空值；空就由服务端用 `agents.default_model`
  与 provider 默认等级。配置里标 `default: true` 的那档才会被预选。
- 每次提交都带 `context.model_name` / `context.reasoning_effort`（走 `runs.create` 的
  `context`，也就是网关的 client switches）；网关再按同一份配置校验一次，
  过期值返回 422 而不是静默忽略。
- 选择存 localStorage（`UserSettings.modelName` / `reasoningEffort`），换会话不清空；
  目录用 TanStack Query 缓存，失败时菜单里显示原因，不阻塞发送。

### 6.6 Artifact 预览要有大小上限

- `ThreadState.artifacts` 是权威的清单
- 文本内容通过 **HTTP byte range 只取前 1 MiB**，后端返回 206
- **被截断的预览要保持轻量**，给一个"加载完整文件"的显式操作，
  **不要为它挂载重型代码编辑器**
- 面板的 UI 状态（开关、选中路径）存 session storage；
  **初始的空流值不能在历史加载完之前覆盖恢复出来的状态**

## 7. nginx 与端口

### 7.1 压缩只给文本，SSE 一律不压

```nginx
gzip on;
gzip_types text/html text/css application/javascript application/json;
# 故意不含：text/event-stream、字体、图片、音视频
```

**SSE 被压缩或被缓冲，体感就是"模型不流式了"**——事件会被攒着批量下发。
字体和图片本来就压过了，再压一遍只费 CPU。

### 7.2 代理层的四个开关

```nginx
proxy_buffering off;              # 响应不缓冲
proxy_cache off;
proxy_set_header X-Accel-Buffering no;   # 告诉下游代理也别缓冲
proxy_set_header Connection '';   # 保持长连接
proxy_http_version 1.1;

proxy_read_timeout 600s;          # run 可能跑很久
proxy_send_timeout 600s;
proxy_connect_timeout 600s;
```

上传路由还要额外加 `proxy_request_buffering off`，
否则大文件会先在 nginx 磁盘上落一遍。

### 7.3 端口绑定必须显式写 loopback

```yaml
# ✗ 绑 0.0.0.0，整个局域网都能访问
ports: ["${PORT:-2026}:2026"]

# ✓
ports: ["${BIND_HOST:-127.0.0.1}:${PORT:-2026}:2026"]
```

**建议写一个测试扫 compose 文件里所有 published port**，断言每一条都有显式的绑定地址。
这种错误肉眼 review 时极容易漏——两种写法只差几个字符。

nginx 本身在容器内监听 `0.0.0.0` 是对的，Gateway 在容器内绑 `0.0.0.0:8001` 也是对的——
它们都是容器内部的，发布出去的那个 nginx 端口才是全部的外部攻击面。

## 8. 测试

### 8.1 单测要分两个环境

| 环境 | 用于 | 占比 |
|---|---|---|
| **node**（纯 JS） | 纯逻辑：顺序合并、状态折叠、消息分组 | 应该是绝大多数 |
| **DOM**（happy-dom 之类） | 需要 document 的：hook、组件 | 尽量少 |

**DOM 环境大约是 node 的 3 倍耗时**，不渲染的测试不要用它。

反过来也有一条：一个行为**只在真实 React 下存在**的 hook
（effect 顺序、卸载清理、store 变化触发重渲染）应该写成 DOM 测试，
而不是一个 mock 掉 React 本身的 node 测试——后者测的是你的 mock。

### 8.2 具体清单

| 文件 | 覆盖 |
|---|---|
| `stream-mode.test.ts` | 不支持的模式抛错而非静默退回；主流被强制成增量模式 |
| `message-order.test.ts` | **seq 优先**；带 seq 的不追加到尾部；低于窗口下界的置顶；**压缩后零共享身份的场景** |
| `stream-state.test.ts` | `updates` 折叠的 reducer 语义和后端一致；无关帧被拒 |
| `message-group.test.ts` | 带正文的工具调用消息；流式期间纯内容消息留在处理中；思考在答案之上 |
| `replay-gap.dom.test.tsx` | gap 触发重载和续订；不表现为正常结束；恢复次数有上限 |
| `e2e/chat.spec.ts` | 拦截后端 API，跑真实的页面交互：发送、流式、工具卡片、刷新续流 |

`message-order.test.ts` 里那条"压缩后零共享身份"是最值得写的——
它是 §4.3 那两次互相打架的修复的和解点，没有它下次重构一定会退回其中一种错误。

E2E 用网络拦截 mock 掉所有后端，不要依赖真实 Gateway——
那样的 E2E 会因为后端的任何改动而红，然后大家就开始忽略它。

## 9. 验收清单

- [ ] 浏览器完成一次带工具调用的多轮对话，工具卡片显示参数和结果
- [ ] **刷新页面，对话继续流式而不是重跑**
- [ ] 写一个大文件（几百 KB），流式输出是分块的而不是每 token 一帧
- [ ] 一个长会话（超过一页历史），滚动加载上一页后顺序正确、没有消息丢失
- [ ] 触发一次上下文压缩，压缩前的用户提问仍然在对话里且位置正确
- [ ] 手动截断 SSE（比如重启 Gateway），界面显示恢复提示并续上，不显示"已完成"
- [ ] 点击停止，侧栏标题正确更新（不是"新对话"）
- [ ] 打开浏览器 DevTools 的 Network，确认 SSE 响应**没有** `Content-Encoding: gzip`

第五条和最后一条建议手工验证一次——前者的自动化成本很高，
后者是那种"配置写对了但实际没生效"的典型。

## 10. 刻意不做的事

| 不做 | 理由 |
|---|---|
| Artifact 的在线编辑 | 要处理草稿、并发冲突、revision 校验。先只读 |
| 多面板（侧边对话、浏览器视图） | 一个可拖拽的多面板布局有大量边界情况（折叠、拖到边缘又拖回来） |
| 多语言 | 先做一种。i18n 的结构成本在只有一种语言时是纯负担 |
| 路由资源预算检查 | 等页面多起来、真的有人加重依赖时再上 |
| 静态演示模式 | 需要一整套 fixture 和 API 打桩层 |
| 结构化人机交互卡片（表单） | M6 的澄清中间件先用纯文本。结构化协议要版本化，值得单独做 |
| 分支、编辑重跑 | 依赖 checkpoint 的分叉能力。等 M4 的血缘跑扎实 |

## 11. 一句话总结

M5 的 UI 部分是常规工作，**真正的风险在"历史 + 实时流"的合并**。

检验标准：**一个长会话，滚动加载历史、触发一次上下文压缩、
刷新页面续流——之后每一条消息都在它应该在的位置，一条都不少。**

这一条过了，剩下的都是可以慢慢打磨的样式问题。
