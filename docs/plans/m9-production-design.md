## 1. M9 是"能演示"到"能上线"的距离

前面八个里程碑做出来的东西，**在你自己的机器上、你一个人用、只开一个进程**时是完整的。
M9 把这三个前提逐个拆掉。

| 线 | 拆掉的前提 | 核心难点 |
|---|---|---|
| **9A 多用户与鉴权** | "只有你一个人用" | 身份的唯一权威来源 |
| **9B 多 Gateway 实例** | "只开一个进程" | 谁有权写终态 |
| **9C 定时任务调度** | "只有人类会发起对话" | 调度状态机 ≠ run 状态机 |
| **9D IM 通道** | "只从浏览器进来" | 什么能发出去 |
| **9E MCP 长时任务**（可选） | "工具调用几秒就返回" | 数据库是真相源 |

### 依赖关系：9A 必须先做

五条线里只有一个硬依赖：**9A 的身份边界要先定**。

9B 的租约按 worker 分、9C 的定时任务属于某个用户、9D 的 IM 消息要映射到 DeerFlow 用户、
9E 的远端任务归属某个人——**全都要引用同一个身份解析结果**。
身份定晚了，后面四条线各自实现一遍，最后四份不一致。

| 周 | 内容 |
|---|---|
| W1 | **9A 身份边界 + 认证门 + 存储分桶迁移** |
| W2 | 9B 租约与孤儿回收（并行：9D 通道骨架） |
| W3 | 9C 调度器（并行：9D 各平台适配） |
| W4 | 9E（可选）+ 四条线的跨线收口测试 |

## 2. 9A 多用户与鉴权

### 2.1 一开始就要定的：身份只有一个权威来源

**客户端传来的任何身份字段一律剥离。** 不是"校验后使用"，是**删掉**。

```python
# Gateway 在构图之前
for key in ("user_id", "owner_id", "auth_user", "auth_user_id"):
    body.metadata.pop(key, None)
    body.config.get("configurable", {}).pop(key, None)
    body.config.get("context", {}).pop(key, None)
```

然后按一条**固定的优先级链**解析真实身份：

```
服务端认证注入的身份  >  运行时上下文里的身份  >  请求 ContextVar  >  default 桶
```

最后那一级只服务于内部调用、内嵌客户端和无 HTTP 的本地执行路径。

**身份要经过一次归一化再用作存储 ID。** 认证系统允许身份是邮箱之类的任意非空字符串，
直接拿去拼目录会出问题（`/`、`..`、大小写、超长）。
做一个 `make_safe_user_id()`：稳定、抗碰撞、目录安全。
原始 identity 留给授权过滤用,归一化后的 ID 给存储用,两者不要混。

**同一个身份解析函数要贯穿全链路**：图构建阶段、中间件执行阶段、记忆、自定义 agent、
技能、技能策略、提示词装配。**图构建和中间件执行落进不同用户桶**是这里最典型的 bug——
它只在多用户环境下出现，单用户测试完全看不出来。

### 2.2 仓储层的默认值是陷阱

```python
# ✓ 默认从当前用户上下文解析
def get(self, thread_id: str, *, user_id: str | Sentinel = AUTO): ...
```

**`AUTO` 绝不能静默退化成全局查询。** 上下文里没有用户时应该报错或返回空，
而不是"那就查全部吧"。后者在一次上下文传递失败时会把所有用户的数据返回给一个人,
而且没有任何报错。

只有**迁移脚本和管理员 CLI** 可以显式传 `user_id=None` 绕过隔离。
把它做成一个显式的、丑陋的、需要特意写出来的参数。

### 2.3 认证门默认拒绝

`AuthMiddleware` 是全局的 fail-closed 门：**不在 public 白名单上的路由一律要求认证**。
新加一条路由默认就是受保护的——反过来（默认放行、要保护的加装饰器）
只要有人忘了加装饰器就是一个洞。

四条配套不变量：

- **JWT 只在 HttpOnly cookie 里传输**，不出现在响应 JSON 里
- 任何非 public 路由**不能只靠"cookie 存在"放行**，必须严格验证
- 用户表上带一个 `token_version`，**不匹配必须拒绝**——这是改密码/重置之后
  让所有旧 session 立刻失效的唯一机制
- CSRF 用 double-submit + 认证 Origin 校验

### 2.4 存储分桶是一次迁移，M2 要为它留好形状

```text
{base}/users/{user_id}/threads/{thread_id}/user-data/{workspace,uploads,outputs}
```

agent 在沙箱里看到的仍然是 M2 定的统一虚拟路径（`/mnt/user-data/...`）——
**用户分桶对 agent 完全不可见**。这是 M2 §3 把虚拟路径映射放在
"每个沙箱实例 acquire 时"而不是全局的原因。

迁移脚本要支持 `--dry-run`、按用户逐个执行、失败继续并在最后返回非零状态。

### 2.5 访问别人的资源返回 404，不是 403

403 泄露了"这个资源存在"。对于 thread ID 这种可枚举的东西,
攻击者可以用 403/404 的差异扫出全部有效 ID。统一返回 404。

### 2.6 平台信任模型：把"谁能代表某用户"收敛到一处

IM 通道绑定和内部认证（服务间直连）本质是同一类东西：
**DeerFlow 把某个渠道视为已认证边界，由它把"自己的用户"映射到 DeerFlow 身份。**

关键约束：**只有认证中间件能授权那个"代表某用户"的内部头**。
任何其它代码路径读到这个头都必须当作普通的不可信输入。

已知边界要在文档里写明：**如果平台把共享密钥下发给了终端，
那个"代表某用户"的头就可以被伪造。** 正确做法是只有平台后端持有密钥,
终端走平台自己的认证。这条不写出来,一定会有人把密钥打进移动端。

## 3. 9B 多 Gateway 实例

### 3.1 一开始就要定的：丢租约之后不准再写终态

这是整条线唯一一个**必须在第一天想清楚**的规则。

一个进程在跑某个 run，网络抖动导致续约失败，租约过期。
此时另一个进程的孤儿回收把这个 run 认领走了、标成了 `error`、给客户端补了 `end`。

**然后原进程的 agent 跑完了，去写"成功"。**

结果：客户端收到了 `end`（error），数据库里是 `success`，SSE 再也不会有第二个 `end`。
这个状态谁也修不了。

规则：

> **一旦本进程确认丢失租约（`ownership_lost`），收尾阶段的所有持久化全部跳过。**
> 这个进程不准再写终态、不准再发 SSE、不准再更新 token 统计。
> 由接管的进程标 `error`（`stop_reason=orphan_recovered`）并补发 `end`。

配套：**所有终态写入都带 `status IN ('pending','running')` 守卫**，先到的赢。
这样即使漏了一条路径，数据库层面也不会被覆盖。

### 3.2 租约的时间语义

```
lease_expires_at 只在 store 续约成功后才前进
```

它的含义是**"最后一次被确认拥有的截止时间"**,不是"我打算持有到什么时候"。
本地时钟往前推一个租约期然后写进内存是错的——续约失败时你以为还持有着。

续约周期建议 `lease_seconds / 3`：允许连续失败两次而不丢租约。

续约失败**且已经过了 deadline** 时：设 `ownership_lost` → 取消本地 run task →
跳过所有收尾持久化。

### 3.3 孤儿回收

```
1. 扫候选：列出 inflight 且租约已过期的行（这是优化，不是权限来源）
2. 每行做 claim_for_takeover：status + 租约过期的原子条件更新
3. 认领成功 → 标 error，stop_reason=orphan_recovered
4. 回调 Gateway：发 END 哨兵、安排 stream 清理
```

第 2 步是关键：**扫描结果不是权限**。两个进程可能同时扫到同一行,
真正的仲裁是那个原子条件更新,只有一个能成功。

触发时机：**进程启动时扫一次** + 心跳每 N 个周期再扫一次。

周期扫描必须是 **single-flight**：上一轮没跑完,下一轮直接跳过。
否则扫描任务会堆积在唯一的那个续约循环上,把续约本身饿死——
这是一个会导致**所有 run 集体丢租约**的故障。

### 3.4 取消在多实例下有三种结果

| 情况 | 结果 | HTTP |
|---|---|---|
| 本进程持有这个 run | 直接中止 | 200 |
| 别的进程持有，租约有效 | 写入持久化的取消请求，等 owner 心跳执行 | 202 |
| 别的进程持有，租约已过期 | 认领后按本地取消处理 | 200 |
| 存储层不支持取消请求 | 拒绝 | 409 + `Retry-After` |

第二种是多实例特有的：**取消请求写进数据库,owner 的心跳循环读到之后执行,
但不转移租约**。转移租约会让两个进程都以为自己在跑。

取消和完成会抢同一行,用 CAS(比较并交换)让先到的赢。

### 3.5 多 worker 的硬前提要在启动时强制

```
多 worker ⇒ Postgres + 事件存储用 DB 后端 + 心跳开启
```

任何一条不满足就**拒绝启动**,不要降级运行。

理由：SQLite 的并发写、内存事件存储、关掉的心跳,这三样在单 worker 下
都是合理的默认值,在多 worker 下都会静默地产生错误结果。
让它启动起来然后偶尔出错,比启动失败糟糕得多。

### 3.6 StreamBridge 换 Redis

M3 §6 定的 StreamBridge 接口在这里换实现。两条要注意：

- **`Last-Event-ID` 的语义不变**：客户端重连时从断点续,
  缓冲区已经滚过去了就发 `GAP` 并终止订阅
- **`publish_end` 的保证不变**：这是 M3 最重要的那条不变量,换实现不能破坏它

另外 checkpoint 的缓存层也要换成 Redis,否则两个实例各自缓存会读到过期状态。

### 3.7 关闭顺序

```
1. 在共享超时预算里优先收用户的 run task（给它们时间正常结束）
2. 停心跳
3. 抽干孤儿回收
4. 停扩展服务(反序) → 停存储 → 停 checkpointer → 停引擎
```

先停心跳再收 run 是错的:心跳停了,租约会在收 run 的过程中过期,
然后本进程自己的 run 会被自己的 `ownership_lost` 逻辑掐掉。

## 4. 9C 定时任务调度器

### 4.1 一开始就要定的：调度器只决定"何时"

> **调度器可以决定什么时候跑,但必须通过既有的 run 路径派发,
> 绝不能引入一条平行的执行栈。**

这条听起来是废话,但违反它非常自然:调度器要跑一个任务,最直接的写法就是
自己组装 agent、自己 astream、自己存结果。然后你就有了两套 run 生命周期,
取消、超时、事件持久化、token 统计全都要实现两遍,而且会不一致。

所有"启动一次 agent 回合"的路径——HTTP、IM、调度器、MCP 通知——
都收敛到 M3 定的那个 `start_run()`。

### 4.2 occurrence 状态机不是 run 状态机

这是 9C 最容易做错的地方。**一次"该跑了"和一次 run 不是一回事。**

```
queued  ──────→  launching  ──────→  running  ──→ (终态)
(持久,重启存活)   (短租约声明)        (已绑定 run)
```

| 状态 | 含义 | 关键性质 |
|---|---|---|
| `queued` | 该跑了,但还没能启动 | **持久化,重启后存活** |
| `launching` | 某个实例声明了启动权 | 短租约;**唯一可以调用启动路径的状态** |
| `running` | 已经绑定到一个 Gateway run | 之后跟随 run 的生命周期 |

为什么需要 `launching` 这个中间态:从"决定要启动"到"run 真的创建出来"
之间有一个窗口,进程在这个窗口里崩溃的话,没有这个状态就无法区分
"还没启动"和"可能已经启动了"。租约过期让它自动回到 `queued`。

**唯一约束:每个 task 最多一个非终态 occurrence。**
数据库层面用 partial unique index（`WHERE status IN ('queued','launching','running')`）强制。
重复触发会自然地合并到那一行上。

### 4.3 忙时排队,不是跳过

早期实现很容易写成"上一次还在跑就跳过这次"。这个语义对用户是错的——
一个每小时跑一次的任务,如果某次跑了 70 分钟,用户期望的是下一次紧接着跑,
不是被静默跳过。

所以忙时持久化为 `queued`,由 `queue_timeout_seconds` 约束等待上限。

**等待中的行不占并发预算。** `max_concurrent_runs` 只计 `launching` + `running`。
让 `queued` 也占预算的话,排队本身会把预算吃光,谁也跑不了。
预算由**原子的队列声明**强制(多实例下用数据库的建议锁做全局上限)。

### 4.4 恢复要用同一个幂等键

每个 occurrence 提供一个**稳定的**运行准入幂等键。
恢复后的重试用同一个键,复用同一条 run,而不是产生第二条。

这直接复用 M3 §5 的幂等机制,不要另做一套。

### 4.5 失败分类

| 启动失败的原因 | occurrence 去向 |
|---|---|
| 线程忙(`ConflictError`) | 退回 `queued`,稍后重试 |
| 其它错误 | 终态 `failed` |

把所有错误都退回 `queued` 会让一个配置错误的任务永远重试。

### 4.6 调度运行是非交互的

后台跑的任务没人能回答澄清问题。所以 `context.non_interactive=true` 时,
lead 的工具集里去掉 `ask_clarification`。

**这个键只对内部认证的调用者生效,客户端传入的一律丢弃。**
否则任何人都能通过这个键改变 agent 的工具集。

### 4.7 活跃状态期间任务定义不可变

`queued` / `launching` / `running` 三个状态下,任务定义(提示词、模型、计划)
都必须冻结。队列准入、修改、暂停、删除这四条路径要串行化。

否则一个正在 `queued` 的 occurrence 会用改过的定义启动,
而用户以为自己改的是下一次。

## 5. 9D IM 通道

### 5.1 一开始就要定的：能发出去的东西是**白名单**

**这是整个 M9 里我认为最值得强调的一条。**

通道要从流里挑出"助手说的话"发给用户。很自然的写法是排除掉不该发的:

```python
# ✗ 黑名单:排除工具消息,其余都发
if "tool" not in payload.get("type", ""):
    publish(text)
```

这是一个**真实发生过的数据泄漏**。原因是 M6 的中间件会往消息流里注入
**隐藏的 `HumanMessage`**:

- 动态上下文中间件把召回的记忆注入为隐藏 `HumanMessage`（`type == "human"`）
- 持久上下文中间件注入 `<durable_context_data>` 隐藏块
- 动态上下文还会重写用户自己的那一轮

这些都不含 `"tool"`,于是全部被发到了群里。实际后果是:
一个 IM 群收到了用户的记忆事实块,另一次收到了用户自己消息的原样回显。

```python
# ✓ 白名单:只有助手消息类型才是可显示文本
ASSISTANT_PREFIXES = ("ai", "assistant")
```

三条实现细节:

- **按前缀匹配,绝不用子串**。普通英文词里就含 `ai`（`chain`、`domain`）
- 要同时认 `AIMessage` 序列化出的 `"ai"`、流式块的 `"AIMessageChunk"`、
  以及外部运行时可能用的 `"assistant"`
- **裸字符串 payload 一律拒绝**:它不带类型信息,无法归属给助手

**在连接器侧再加一道防御:发送前检查文本里有没有隐藏上下文的包装标记**
（`<memory>`、`<durable_context_data>`、`<system-reminder>`）,有就拒绝并记 ERROR。
对于消息不可撤回的平台（比如公开的中继网络）,这一道是最后的挽救机会。

### 5.2 三种投递策略

| 策略 | 适用 | 实现 |
|---|---|---|
| **等最终回复** | Slack、Discord | `runs.wait()`,拿到终态再发一条 |
| **流式改卡片** | 飞书、Telegram、钉钉 | `runs.stream()`,原地编辑同一条消息/卡片 |
| **发射后不管** | Webhook 驱动的场景 | `runs.create()` 返回即走,agent 自己写回 |

流式那一类要注意各平台的限流(比如群里的每分钟消息数上限)和长度截断。
被限流丢掉的中间更新是可以接受的,**但最终那一次必须成功**。

发射后不管那一类没有 outbound,所以"线程忙"的提示用户看不见——
需要一个 per-thread 的缓冲把并发消息攒起来,等当前 run 结束后合并成一次追加输入。
**这个缓冲是进程内的,多 worker 下有已知缺口**,要写进文档。

### 5.3 身份穿透要走显式参数

IM 消息带三样东西:`connection_id`、`owner_user_id`（DeerFlow 用户）、
`channel_user_id`（平台上的原始发送者 ID)。

**owner 必须通过显式的 `user_id=` 参数一路穿透下去,不能依赖请求上下文。**
通道 worker 跑在自己的循环里,请求 ContextVar 在那里是空的或者是错的。

文件上传、产物投递、记忆桶——每一处都要显式传。少传一处,
那个用户的文件就会落到 default 桶,agent 读不到。

`channel_user_id` 有两条纪律:

- **只从内部认证的调用者的顶层 context 接受**,从自由形式的配置段里一律清除
- **只写进运行时上下文,绝不写进 `configurable`**——后者会进 checkpoint,
  等于把群里某个人的平台 ID 永久写进对话历史

### 5.4 绑定码的安全模型

用户在浏览器里点"绑定 Telegram",拿到一个一次性码,在聊天里发 `/connect <code>`。

**绑定码的消费必须发生在 `allowed_users` 过滤之前**,否则一个刚被加进白名单
但还没绑定的用户永远没法完成第一次绑定。

推论要写明:**`allowed_users` 不是绑定期的防御**。任何持有有效码的人都能消费它。
绑定的安全性完全建立在码的机密性上:足够的随机性、短 TTL（10 分钟）、
一次性消费、**只在发起绑定的那个浏览器里显示,绝不回显到聊天里**。

`allowed_users` 仍然守着普通消息。

### 5.5 一个外部身份只能有一个活跃 owner

外部身份的键是 `(平台, 外部账号 ID, 工作区)`。**最新一次成功绑定获胜**,
绑定时撤销其它 owner 的活跃行。

这个不变量要用**数据库的 partial unique index**（`WHERE status != 'revoked'`）强制,
不能只靠应用层逻辑。两个 owner 并发绑定同一个身份时,
只有一个能成功,输的那个针对已经可见的新状态重试。

## 6. 9E MCP 长时任务（可选）

远端 MCP 工具可能要跑几十分钟。让 agent 在工具调用里等着是不可接受的——
run 会超时,而且中间不能做别的事。

核心设计（M7 §9 已经把它列为"不做",这里是它真要做时的形状）：

- **agent 只负责 submit**。submit 的包装器在持久化远端句柄之后,
  只返回一个本地任务 ID。状态查询和取消工具对模型隐藏
- **数据库是真相源**。租约轮询在 Agent/LLM 循环之外跑
- **`ThreadState` 只收到有界的当前线程投影**,不是全量任务列表
- 远端完成后,Gateway 开一次**通知 run** 把结果说回对话

三条容易错的:

**租约过期是重启恢复机制。** 一个在租约过期后才返回的状态结果必须丢弃,
**即使 owner token 还匹配**。

**轮询时间戳基于远端调用的完成时刻,不是扫描开始时刻。** 一次慢的远端调用
会把重试间隔吃掉。

**提交成功但持久化失败时要尽力取消远端任务。** 否则那个任务会一直跑,
而我们已经没有它的句柄了。补偿失败时保留原始错误。

## 9. 刻意不做的事

| 不做 | 理由 |
|---|---|
| 细粒度 RBAC | 先只有 `admin` / `user` 两个角色。细粒度权限的模型要等真实的组织结构需求 |
| 跨进程的 IM 忙时缓冲 | 需要共享缓冲存储或通道 leader 选举。单进程部署没有正确性问题,写进已知边界 |
| 分布式限速 | 进程内计数在单 worker 精确、多 worker 近似。够用之前不引入 Redis 限速器 |
| Kubernetes / 微服务化 | 见路线图"最容易走错的三个岔路"第 3 条。分布式的复杂度要等真实并发压力 |
| 9E MCP 长时任务 | 整套租约 + 轮询 + 通知投递的状态机。除非确实有跑几十分钟的远端工具 |
| IM 的双向富交互（按钮、表单） | 每个平台一套 API,收益远小于投入 |

## 10. 一句话总结

M9 五条线各有难点,但只有两个错误是**不可恢复**的:

1. **丢租约的进程继续写终态** → 数据库和客户端永久不一致,没有任何机制能修
2. **通道用黑名单决定什么能外发** → 用户的记忆和隐藏上下文泄漏到外部平台,
   在不可撤回的平台上永久留存

其余的（身份桶错了、调度重复触发、绑定冲突）都能靠修数据恢复。
把评审的注意力压在这两条上。
