## 1. M10 是什么性质的一段

前面九个里程碑做的是**功能**：能对话、能用工具、能流式、能持久化、能扩展能力、能委派。
M10 做的是**长期正确性**——让系统在跑了三个月、积累了几千条记忆、装了五个插件之后，
仍然是可信的、可解释的、可回滚的。

这四条线的共同特征：**演示时完全看不出差别，上线三个月后决定你能不能继续往前走。**

| 线 | 一句话 | 不做的后果 |
|---|---|---|
| **10A 记忆** | 跨 thread 记住用户的事实 | 每次对话都从零开始 |
| **10B 护栏与审计** | 约束和记录 agent 做了什么 | 出事之后查不出来 |
| **10C 扩展插件** | 第三方能贡献中间件/路由/服务 | 所有定制都要改主干代码 |
| **10D 可观测与评测** | 看得见、可复现地度量 | 改了策略不知道变好还是变坏 |

四条线**互不阻塞**，可以四个人并行。但每条线都有**一个装了就很难改**的决定，
下面每节的第一小节就是那个决定。

### 排期建议

| 周 | 内容 |
|---|---|
| W1 | 10C 扩展契约（其它三条都可能想贡献扩展点，先定契约）+ 10D 追踪接线 |
| W2 | 10A 记忆的抽取安全门 + 存储契约 |
| W3 | 10A 检索与容量淘汰 + 10B 护栏与审计 |
| W4 | 10D 离线基准 + 四条线的收口测试 |

10C 排在最前面不是因为它最重要，而是因为**契约定晚了会返工**。

## 2. 10A 持久记忆

### 2.1 一开始就要定的：抽取安全门

**记忆是整个系统里唯一一个"根据模型输出、不经用户确认就写入持久存储"的模块。**

这一句话决定了它的设计重心。不是检索质量，不是存储格式——是**什么东西允许被自动写进去**。

方案：抽取出来的每一条提议都必须带三个标签，三者同时满足才允许自动写入。

| 标签 | 允许自动写入的值 | 被挡掉的例子 |
|---|---|---|
| `scope` | `user`（用户级） | `task`（这次任务的临时结论）、`project` |
| `durability` | `durable`（长期有效） | `ephemeral`（"我现在在开会"） |
| `authority` | `descriptive`（陈述事实） | `normative`（"以后都要用中文回答"——这是指令不是事实） |

三条纪律：

**缺标签就拒绝那一条，但不要中断其它条。** 一批抽取里有 5 条，其中 1 条缺标签，
正确行为是写入另外 4 条并计数拒绝——不是整批失败。

**矛盾删除要 fail closed。** 模型可以提议"这条旧事实和新事实矛盾，删掉它"，
但 `task` 和 `project` 作用域的删除提议一律拒绝。成对的"删除 + 替换"里，
如果替换项没通过所有写入门，删除也不执行。

**自定义提示词模板必须包含同样的分类字段。** 有人换了提示词但忘了分类字段，
抽取会 fail closed（全部拒绝）而不是 fail open（全部放行）。
配一个拒绝率计数器和高拒绝率告警，否则这种情况会静默地让记忆停止增长。

### 2.2 存储布局：一条事实一个文件

```
{base}/users/{user_id}/memory.json                          # 只存共享摘要 + 版本
{base}/users/{user_id}/agents/{agent}/facts/{prefix}/{id}.md  # 一条事实一个 markdown
```

**`memory.json` 绝不存事实，也不存事实索引。**

为什么不用一个大 JSON：记忆是**高频小改**的数据。加一条事实要重写整个文件，
并发下要么加全局锁（慢），要么丢更新。一条事实一个文件让定向写只碰选中的那几个文件。

配套的并发契约：

- 写入用**用户级锁 + 共享版本号 + 每条事实的版本号 + 恢复日志**
- **点操作**（改一条）只在所有原始事实的前置条件仍然成立时才能 rebase
- **快照操作**（全量重算）遇到清单冲突必须重新加载并重算
- 用类型化的冲突异常，**不要靠匹配异常文本**判断冲突种类
- POSIX 原子替换之后要 **sync 父目录**（否则崩溃可能丢掉目录项）

还有一条容易忽略的：`apply_changes()` 这类返回增量的接口要显式标注
`complete: false`，**绝不能把一份局部缓存标成完整的记忆文档**。
调用方只在自己的响应契约确实需要完整文档时才重新加载。

### 2.3 两种工作模式

| 模式 | 谁决定写 | 注入什么 |
|---|---|---|
| `middleware`（默认，被动） | 框架按规则排队抽取 | 共享摘要 + 当前 agent 的事实 |
| `tool` | 模型自己调 `memory_search` / `memory_add` / … | 只有共享摘要 |

tool 模式故意**不**把事实注入提示词——它们藏在 `memory_search` 后面，模型要用才去查。
这省 token，但代价是模型可能想不起来去查。

tool 模式下**仍然保留被动写入**（在支持的后端上）。两种模式不是互斥的。

**tool 模式的 CRUD 不走抽取安全门**——那是用户通过模型显式表达的意图，
和被动抽取的信任级别不同。这是有意的，要在文档里写明。

### 2.4 容量淘汰必须可评测

事实会一直增长，到了上限就要淘汰。**淘汰策略是这个模块里唯一一个
"改了之后没法靠直觉判断好坏"的部分。**

所以从第一天起就要求：

- 所有路径（自动、手动、工具、导入）**共用同一个淘汰函数**。
  四个地方各写一遍淘汰逻辑，评测就失去意义了
- 新策略先上 **shadow 模式**：记录新旧策略的分歧，但仍然执行旧策略
- 配一个离线基准（比如 LongMemEval 这类长期记忆评测集）跑策略对比

### 2.5 "确认"只能由确定性逻辑产生

淘汰策略通常会用到"这条事实最近被确认过吗"。
**确认信号绝不能由模型自己声明。**

模型的输出只提供**绑定**（"这次对话印证了第 3 条事实"），
真正的确认门是确定性的：比如"最近 6 条过滤后的消息里有一条人类消息"。

否则模型可以通过反复声明"我确认了这条"来让任意事实永久免疫淘汰。

同理，**访问热度只由搜索命中递增**——提示词注入和 `get_context()` 不递增。
不然所有被注入的事实热度会一起涨，这个信号就没有区分度了。

### 2.6 检索索引必须是可重建的派生数据

检索索引（全文索引之类）放在一个明确标记为可重建的子目录下。三条降级路径：

- 索引更新失败 → 把该作用域标脏，搜索退化为规范的子串匹配，直到重建成功
- 重建致命失败 → 保持惰性重试，不要让整个记忆模块不可用
- 索引库损坏 → 删掉重建一次

**存储要在释放持久锁之后才发送索引更新。** 在锁内更新索引意味着索引的
I/O 延迟直接计入写锁持有时间。

启动时预热索引，但**不要让预热阻塞就绪探针**。

### 2.7 几个具体的坑

**身份必须由服务端决定。** 客户端传来的身份键（`user_id` 之类）要在构图之前
被 Gateway **删除**，服务端认证得到的身份优先。
记忆、自定义 agent、用户技能、技能策略、提示词装配都复用同一个身份解析函数。

**子代理会污染父 thread 的记忆。** 见 M8 §8.4——子代理共享父 `thread_id`，
构建子代理链时要显式跳过记忆刷写钩子。

**注入块要有内容哈希。** 每次 run 对生效的隐藏记忆块算一次哈希，
记一条 `context:memory` 事件带 `content_sha256`，完整文本留在 checkpoint 里。
这样事后能回答"那次回答时模型看到的是哪版记忆"。
Gateway 要**剥掉客户端伪造的动态上下文标记**。

**token 计数不要在热路径上下载东西。** 默认用 tiktoken，惰性加载并缓存；
加载失败退化为字符估算并进入冷却期（比如 600 秒），冷却期内不重试。
提供一个 `token_counting: char` 配置项，让离网部署彻底不碰网络。

## 3. 10B 护栏与审计

### 3.1 一开始就要定的：证据的分层

护栏这条线最容易做成"一堆散装的检查"。要避免这个，先定一个分层：

| 层 | 做什么 | 能证明什么 |
|---|---|---|
| **提示词层** | 要求 agent 在声称做了某事时附上回执引用 | 什么都不能证明，但让下一层非空转 |
| **确定性层** | 代码校验引用的回执确实存在、工具确实被调用过 | "这个工具确实被调用了" |
| **重执行层** | 重新跑一遍验证结论 | "结论是对的" |

**M10 只做前两层。** 第三层是独立的产品线。

关键在于**理解第二层的边界**：它证明的是"执行发生过"，
**不是**"声称的结论是正确的"。一个 Makefile 吞掉了失败、一个测试脚本
失败也退出 0——这些第二层都看不出来。

这个边界要写进代码注释和文档，否则半年后会有人以为回执校验等于结果正确。

### 3.2 工具回执台账

每次工具调用产生一条回执：一个稳定的短 id（`r1`、`r2`…）、工具名、
有界的参数摘要、状态。回执台账挂在消息元数据上，随 checkpoint 持久化。

提示词层要求 agent 在说"我写了 report.md"时写成 `[r7 write_file]`。
确定性层校验 `r7` 存在、确实是 `write_file`、且状态成功。

三条实现纪律：

**回执 id 的格式必须由单一来源生成，提示词里的示例也从那个来源派生。**
手写一个示例格式，改了生成器之后提示词会静默地教模型用错格式。

**证据有界，截断就降级为"无法验证",不要当成通过。**

**回执要在终态化之前收割并和其它字段在同一把状态锁下提交。**
否则状态轮询可能先看到终态、后看到回执元数据。

### 3.3 沙箱审计与工作区变更

沙箱审计中间件记录每一次沙箱操作：命令、路径、结果概要。这是事后取证的唯一来源。

工作区变更记录要能回答"这次 run 改了哪些文件"。两条：

- **排除内部命名空间**（临时目录、`.git`、`node_modules` 这类）。
  按**目录名在任意深度**匹配，不要只匹配根下的那一层——
  MCP 服务器可能从别的 cwd 创建一个相对路径的内部目录
- diff 要有大小上限，超了就只报文件列表

### 3.4 安全性终止原因要和普通终止区分

provider 的内容过滤触发时，返回的 `finish_reason` 和正常结束是不同的。
把它当普通结束处理会让用户看到一条空回复，完全不知道发生了什么。

要单独识别并转成一条明确的、用户可读的说明。同理还有长度截断
（`finish_reason=length`）——那是"没说完"，不是"说完了"。

## 4. 10C 扩展插件系统

### 4.1 一开始就要定的：插件列表放在哪

**插件列表放 `config.yaml` 的顶层 `plugins:`，不放 API 可写的 JSON。**

理由很硬：这个列表会导致 **Python 入口点被 import**，也就是**代码执行**。
M7 的 `extensions_config.json` 是 Gateway API 可写的，
把插件列表放进去等于给了 API 调用方任意代码执行。

配套：**插件加载是启动期的，任何变更都需要重启。** 不要试图做热加载——
Python 的模块卸载不可靠，一个热重载的插件会留下半个旧版本的类对象在内存里。

### 4.2 `required: true` 是显式选择，默认必须是 false

一个标了 `required: true` 的插件加载失败时，Gateway 启动会中止。
失败的原因可能是坏掉的 wheel、缺失的本地库、被删掉的源码快照——
这些都会变成**只能通过 shell 访问才能恢复**的启动失败。

所以托管安装写入的记录一律是 `required: false`，
`required: true` 只能通过显式的 `--required` 选择。
接管一条手写记录时保留运维已经选的值。

### 4.3 公共契约包不许 import 框架

```
packages/extension-api/     # 公共契约，绝不 import 框架，也不带框架依赖
packages/harness/           # 框架
```

扩展自己声明它要用的 FastAPI / LangChain / LangGraph 依赖。
契约包一旦依赖框架，扩展作者就被锁死在框架的版本区间里。

### 4.4 中间件贡献用语义锚点，不用列表下标

```python
# ✗ 下标在宿主插入一个新中间件时就错位了
registry.add_middleware(MyMiddleware(), index=7)

# ✓ 声明语义位置，由宿主解析
registry.add_middleware(
    MyMiddleware(),
    scope="lead",
    placement=Placement.TOOL_VISIBLE,
    order=100,
)
```

参考 M6 §3 的分区语义定义几个锚点（模型逻辑层、模型物理层、
工具可见层、工具原始层、普通层），扩展声明自己属于哪个分区加一个稳定序号。

四条配套纪律：

**单一最终组装点。** 扩展的注入必须发生在组装的**最后一步**，
不能注在共享的基础构建器里——lead 的构建器在那之后还会追加中间件。

**依赖方向不能反。** `extensions/` 在 `agents/` 下面，
所以 `extensions/` 里**任何模块作用域**都不许 import `agents.middlewares`。
需要引用中间件类的表（顺序约束表、锚点表）要**延迟到首次调用时解析**。
注意是延迟**调用**，不要用一个惰性容器假装已解析——
那种东西迭代时报一个答案、测长度时报另一个。

**贡献的中间件要被隔离包装，fail open。** 扩展失败时发诊断信息、
继续往下走，**不能重复下游的模型/工具副作用**。
包装器要镜像内层实现的所有生命周期钩子、工具、转换器和状态 schema。

**同步/异步要成对。** LangChain 把每一对 sync/async 包装器当作**一个**能力，
只实现一边会收到一个直通的另一边。要观察两条执行路径就得两边都实现。

### 4.5 fail-open 按失败的**来源**判断，不按异常基类

这是整个 10C 最微妙的一点。

`CancelledError` 到达贡献者的 `except` 有两个完全无关的原因：

1. 宿主任务真的被取消了 → **必须传播**
2. 扩展自己用取消实现了一个内部超时，泄漏了出来 → **必须包住**

按基类判断（`except CancelledError: raise`）会让第 2 种情况跳过后续贡献者，
而且会走到 worker 的延迟中断路径，把一次本来成功的 run 标成已取消。

正确做法是判断**是不是宿主任务的真实取消**（Python 有
`asyncio.Task.cancelling()` 可以区分）。`KeyboardInterrupt` / `SystemExit` 照常传播。

### 4.6 贡献的 HTTP 路由

**最后挂载，宿主永远赢。** 贡献的路由在所有宿主路由之后挂载。

**保守的遮蔽检测。** 如果一条贡献路由会被已有路由遮蔽，整个 router 原子拒绝。
检测只在**能证明**遮蔽时才拒绝——需要一般正则包含关系才能判断的情况一律放行，
不要猜。

**贡献的路由强制会话认证，不能 opt out。** 扩展通过一个投影
（用户 id、管理员标志、内部标志、角色）区分调用方，**拿不到宿主的认证上下文**。

**生命周期资源只能用扩展服务，不能用 router 的 lifespan。**
拒绝贡献的 startup/shutdown 钩子和自定义 lifespan。

### 4.7 安装事务

如果要做 CLI 安装（`install` / `list` / `enable` / `disable` / `remove`），
有三条不做会出事的：

**在跑包管理器之前先校验配置文件。** `uv add` / `pip install` 会执行包的**构建后端**——
也就是任意代码。一个这个管理器永远写不进去的配置，
必须在那段代码跑起来**之前**失败，而不是之后靠回滚。

**本地目录安装是快照，不是可编辑链接。** 复制到一个受管目录下，
忽略 git 元数据、虚拟环境、字节码；拒绝符号链接、路径逃逸的包名、
以及看起来像凭据的文件。

**安装后要审计锁文件。** 源地址校验拦不住环境驱动的解析
（比如一个 `UV_FIND_LINKS` 指向的本地 wheel 仓库会把一个普通的包依赖
变成本地 wheel 引用）。生产镜像构建复现不了的本地引用要让整个事务回滚。

> 和 M7 §4.5 一样的提醒：**这些检查防的是打包事故，不是恶意代码。**
> 构建钩子和扩展代码都以 Gateway 权限执行，真正的边界是"只接受可信的运维来源"。

## 5. 10D 可观测性与评测

### 5.1 追踪回调挂在图的调用根上，不是模型上

这一条 M1 §7 已经定了，M10 是把它落实并扩展。重申原因：

基于 OTel 的追踪 provider 只在看到 `on_chain_start(parent_run_id=None)`
时才把保留的追踪属性提升到根 trace 上。挂在模型层意味着那些属性永远不生效，
而且一次 run 会产出一堆互不相关的 trace 而不是一棵带子 span 的树。

**图外的模型调用是例外**：记忆抽取、标题生成、摘要、目标评估这些不经过图，
它们保留模型级的回调挂载。

**子代理的 trace 要归到父 thread 的会话卡片下**：带上父 `thread_id`
作为会话 id、在委派时捕获的 user_id、以及一个 `subagent:<name>` 的 trace 名。

### 5.2 进程级全局的 provider 只能从 lifespan 初始化

有些 telemetry 库（OTel 系的）初始化时会装一个**进程级全局的 TracerProvider**、
打补丁改序列化、自动 instrument 各种客户端。

这类一次性的全局副作用**只能从 Gateway 的 lifespan 调用**，
绝不能从 `build_tracing_callbacks()` 或任何模块的 import 期触发。

写一个测试钉住：**`import agentkit.agents` 不许启动任何追踪。**

代价要说清楚：这种 provider 只覆盖 Gateway 路径，
内嵌客户端和 CLI 不被 instrument——那些用户要自己调初始化函数。

### 5.3 离线基准的六条纪律

基准脚本可以 import 它要度量的生产函数，**但绝不能复制一份平行的实现**。
一旦复制，基准度量的就不是生产行为了。

| 纪律 | 具体要求 |
|---|---|
| **数据集钉死** | 按不可变 revision + SHA-256 固定；路径由调用方提供，**评测命令不许静默下载** |
| **不提交敏感内容** | 不提交上游数据集文本、凭据、完整 provider 请求、响应头。提交的清单只能有稳定 ID 和来源定位符 |
| **配置版本化** | 模型 ID、推理参数、提示词、重试规则、时钟、随机种子全部写进评测配置 |
| **结果分级** | 公开结果可含 case ID、策略决策、模型假设、评分、非机密元数据；数据集问题、参考答案、记忆内容、完整 payload 留在被 gitignore 的本地目录 |
| **确定性** | 固定时钟 + 确定性排序；结果记录所用的配置、清单、提示词、数据集和 git revision |
| **离线套件独立** | 单元测试**不许**依赖网络、凭据或真实数据集。小规模的数据集形状 fixture 必须是合成的，且自我标注为合成 |

最后一条最容易被违反：有人把真实数据集的几条样本贴进测试文件当 fixture，
然后这个仓库就永远带着一份不该有的数据了。

### 5.4 基准要覆盖的两类东西

| 类型 | 例子 | 为什么需要 |
|---|---|---|
| **策略质量** | 记忆淘汰策略的新旧对比 | §2.4 说的，改了没法靠直觉判断 |
| **并发争用** | 多**进程**（不是 asyncio 任务）打同一张表，SQLite vs Postgres | M4 说 SQLite 只适合开发，这是那个结论的证据 |

并发基准有两个实现细节：worker 要**直连数据库**跳过迁移引导
（编排器已经跑过一次了），以及所有 worker 要在计时之前用一个 READY/GO 屏障对齐，
否则测的是进程启动的参差而不是争用。

- [ ] 一批抽取里混入 `task` 作用域和 `normative` 的条目，它们被拒绝，其它条目正常写入
- [ ] 换掉记忆提示词模板但漏掉分类字段 → 抽取 fail closed，且拒绝率告警触发
- [ ] 两个进程同时写同一个用户的记忆，没有丢更新
- [ ] 一个故意抛异常的扩展中间件，run 正常完成，诊断信息可见
- [ ] 一个贡献路由试图遮蔽宿主路由 → 整个 router 被拒绝，其它扩展的 router 照常挂载
- [ ] 一次 run 在追踪后台呈现为**一棵**树，子代理归在同一个会话下

但"呈现为一棵树"这件事只有肉眼能确认。

## 8. 刻意不做的事

| 不做 | 理由 |
|---|---|
| 重执行式的结论校验 | §3.1 的第三层。独立产品线，工作量和前两层不是一个量级 |
| 插件热加载 | Python 模块卸载不可靠，热重载会留下半个旧版本在内存里 |
| 插件的原地升级 | 保留私有配置 → 卸载旧的 → 装新的 pin → 恢复配置。做原地升级要处理配置迁移 |
| 向量检索的记忆 | 先用全文索引。向量检索引入嵌入模型依赖、索引重建成本和一个新的质量维度 |
| 记忆的多后端适配 | 先把自己的本地后端的契约跑扎实，再谈适配远端服务 |
| 贡献 WebSocket 路由 | 宿主还没法给贡献的 WS 提供认证和 Origin 校验 |

最后一条是一个通用的原则：**宁可拒绝一种贡献，也不要接受一种宿主会静默忽略的注册方式。**
任何新增的贡献种类，公共契约和宿主运行时必须在**同一个改动**里都实现。

## 9. 一句话总结

M10 四条线的共同主题是**让系统在长期运行后仍然可信**，
而每条线的核心都是同一种取舍：**在不确定的时候拒绝，而不是放行。**

- 记忆：标签不全就不写
- 护栏：证据被截断就报"无法验证"，不报通过
- 扩展：遮蔽宿主路由就整个拒绝；分不清是不是真取消就按能证明的那条走
- 评测：数据集没钉死就不跑

这四个 fail-closed 的选择，是这个阶段唯一真正需要坚持的东西。
